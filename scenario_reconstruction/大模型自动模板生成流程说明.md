# 大模型自动模板生成流程说明

本文说明当前新增的自动流程：从 Autoware 的 `metadata.yaml` 和 `.db3` 数据出发，通过大模型推理批量生成事故模板，再接入已有的变体生成与碰撞评分流程。

## 1. 当前输入数据

当前默认输入是仓库根目录下这两个文件：

```text
metadata.yaml
2019_07_9_cuted_run01_0.db3
```

它们来自同一个 ROS2 bag：

```text
metadata.yaml：bag 元信息，包括 topic、消息数量、持续时间、db3 相对路径
2019_07_9_cuted_run01_0.db3：sqlite3 格式的 ROS2 bag 数据库
```

当前代码会从 `.db3` 中读取：

```text
topics 表
messages 表的 topic_id、timestamp 统计信息
每个 topic 的消息数量、首尾时间、消息频率
```

当前已经识别出的重要 topic 包括：

```text
/localization/kinematic_state
/vehicle/status/velocity_status
/perception/object_recognition/objects
/planning/scenario_planning/trajectory
/control/command/control_cmd
/tf
/tf_static
/clock
```

## 2. 当前能自动抽取什么

当前新增的摘要器在：

```text
scenario_reconstruction/autoware_summary.py
```

它会生成：

```text
Autoware bag 持续时间
总消息数
topic 列表
每个 topic 的消息数量
每个 topic 的时间跨度
每个 topic 的频率估计
当前可用信号类型
当前仿真环境限制
给大模型的模板生成提示
```

本机验证中，当前 bag 的摘要结果是：

## 3. 当前不能自动抽取什么

当前 D2RL conda 环境里没有这些 ROS2 反序列化组件：

```text
rosbag2_py
rclpy
rosidl_runtime_py
```

因此目前还不能直接把 `.db3` 里的 CDR blob 解码成：

```text
精确自车轨迹
精确目标车轨迹
目标车尺寸
感知框位置
碰撞瞬间真实 Autoware 状态
控制命令真实数值
```

所以当前大模型输入是“bag/topic 级摘要 + 当前仿真环境约束”，不是完整的 Autoware 轨迹数据。后续如果在 ROS2 环境中补上消息解码，就可以把几何轨迹、目标车状态、故障发生时刻等更强信息一起交给大模型。

## 4. 大模型如何接入

当前新增的大模型模板生成器在：

```text
scenario_reconstruction/llm_template_generator.py
```

它使用 Qwen / DashScope 的 OpenAI-compatible HTTP 接口，不依赖 `openai` 或 `requests` 包。

代码读取环境变量：

```text
DASHSCOPE_API_KEY
```

也兼容：

```text
QWEN_API_KEY
```

可选环境变量：

```text
QWEN_BASE_URL
```

如果没有设置 `QWEN_BASE_URL`，默认使用：

```text
https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions
```

默认模型：

```text
qwen-plus
```

在 PowerShell 中可以这样临时设置：

```powershell
$env:DASHSCOPE_API_KEY="你的 DashScope API Key"
```

注意：不要把 API key 写进代码、模板、README 或提交记录里。

## 5. 大模型输出什么

大模型现在不再被强制要求只能输出 JSON 数组。

允许两种形式：

```text
直接输出 JSON 数组
输出 JSON object，并在 templates / scenario_templates / candidates 中放模板数组
```

这样做是为了减少格式约束，让模型有更多空间表达自己的事故场景推理。

每个模板必须满足当前 `ScenarioTemplate` schema：

```text
template_id
description
map
route
duration
tags
ego
actors
events
perturbations
```

当前不再在模型输出后强行改写：

```text
map
route
lane_index
events
```

也就是说，如果模型推理出复杂地图、其他 route、更多事件类型，这些原始结果会被保留在 `template_generation_manifest.json` 的 `candidates` 中。

但是当前能进入 SUMO/NADE 仿真的模板仍然需要满足当前项目限制：

```text
map 必须是 2Lane
route 必须是 route_0
lane_index 只能是 0 或 1
ego id 使用 CAV
至少包含 BV_cut_in
必须包含 forced_bv_action
perturbations 只支持 uniform 数值增量扰动
```

原因是：当前 SUMO/NADE 重建环境真正跑通的是 `2Lane + forced_bv_action + 扰动扩增 + 碰撞评分` 这条链路。

如果模型生成的模板不满足这些限制，流程不会直接丢弃原因，而是记录：

```text
candidate_index
template_id
status = usable / unusable
validation_error
raw_template
candidate_template
```

这样可以评估模型到底是“推理失败”，还是“推理出了当前仿真环境暂时跑不了的更复杂场景”。

### duration 如何计算

现在 prompt 会明确告诉大模型不要随便填 `duration=0`，而是区分两类 duration：

```text
scenario.duration：整个仿真场景的持续时间
event.duration：某个故障或动作事件的持续时间
```

`scenario.duration` 的优先计算方式：

```text
优先使用 autoware_summary.duration_s
或者使用 (所有 topic 的最大 last_timestamp_ns - 最小 first_timestamp_ns) / 1e9
然后裁剪到当前可运行的仿真窗口，例如 6 到 20 秒
```

`event.duration` 的优先计算方式：

```text
如果有解码后的事件起止时间：
event.duration = (event_end_ns - event_start_ns) / 1e9
```

如果暂时没有 ROS2 CDR 解码，只能看到 topic 级统计，则用帧数和频率估计：

```text
event.duration = frame_count / relevant_topic_rate_hz
```

其中 `relevant_topic_rate_hz` 可以来自：

```text
/perception/object_recognition/objects
/control/command/control_cmd
/vehicle/status/velocity_status
/localization/kinematic_state
```

对当前 cut-in 的 `forced_bv_action`，如果没有解码轨迹，prompt 会要求模型按感知和控制采样率估计：

```text
duration = max(0.5, min(2.0, 8 / min(perception_objects.bag_rate_hz, control_command.bag_rate_hz)))
```

在当前 bag 中，近似有：

```text
perception_objects.bag_rate_hz ~= 7.05 Hz
control_command.bag_rate_hz ~= 15.16 Hz
```

因此：

```text
8 / min(7.05, 15.16) ~= 1.13 s
duration ~= 1.13 s
```

如果这些频率也缺失，才使用保守默认值：

```text
duration = 0.8 s
```

同时要求模型把计算依据写入事件参数：

```json
"params": {
  "lateral": "left",
  "longitudinal": 0.0,
  "apply_once": false,
  "duration_basis": "estimated as 8 / min(perception_objects.bag_rate_hz, control_command.bag_rate_hz)"
}
```

这样后续检查模板时，不仅能看到 `duration` 是多少，还能看到它是根据哪些记录量、用什么公式算出来的。

## 6. 如果大模型不可用怎么办

如果没有设置 key、网络不可用、模型返回不是合法 JSON，默认会自动走 fallback 模板生成。

fallback 会生成当前已经跑通的 cut-in 模板族：

```text
autoware_fallback_cut_in_0000
autoware_fallback_cut_in_0001
...
```

这些模板仍然会进入后续校验、变体生成和碰撞评分流程。

这保证了：即使暂时不能调用 Qwen，整条工程流程也可以在本机验证。

如果要专门评估大模型，不想让 fallback 掩盖模型失败，可以加：

```powershell
--disable_fallback
```

例如：

```powershell
conda run -n D2RL python -m scenario_reconstruction.run_auto_analysis --metadata metadata.yaml --db3 2019_07_9_cuted_run01_0.db3 --output_root data_analysis\raw_data\AutowareAutoAnalysisQwenEval --templates 5 --variants 1 --disable_fallback --skip_simulation
```

如果没有设置 key，结果会记录为：

```text
generation_source = llm_unavailable
llm_error = DASHSCOPE_API_KEY or QWEN_API_KEY is not set.
usable_template_count = 0
```

## 7. 自动流程入口

总入口在：

```text

```

只生成摘要和模板，不跑 SUMO：

```powershell

```


## 8. 输出结构

自动流程会生成：

```text
output_root/
  auto_analysis_summary.json
  summary/
    autoware_summary.json
  templates/
    *.json
    template_generation_manifest.json
  batches/
    <template_id>/
      batch_summary.json
      variants/
      episodes/
```

其中最重要的是：

```text
summary/autoware_summary.json：给大模型的 Autoware 输入摘要
templates/*.json：大模型或 fallback 生成的事故模板
batches/<template_id>/batch_summary.json：变体运行与碰撞评分结果
auto_analysis_summary.json：整个自动流程的总摘要
```

其中 `auto_analysis_summary.json` 现在还会包含 `evaluation` 字段：

```text
generation_source
llm_error
raw_candidate_count
usable_template_count
unusable_template_count
unusable_error_counts
successful_runs
failed_runs
training_ready_crashes
best_outcomes
```

这部分就是用来判断“大模型是否能支持事故模板生成任务”的核心评估结果。
